Add an endpoint under Settings → Integrations, tick the events you want, and
Sailo will `POST` signed JSON to it. Anything that accepts a webhook works —
Zapier's *Catch Hook*, n8n's *Webhook* node, Make's *Custom webhook*, Pipedream,
or your own server.

## Events

<EventCount /> events, listed from the same constant the delivery code filters
subscriptions against.

<EventList />

On a card sale `order.created` and `order.paid` arrive together, when the
payment lands — not when the buyer opens the checkout, because a third of those
are abandoned. On bank transfer, cash or any other manual rail, `order.created`
fires at checkout and `order.paid` when you confirm the money arrived.

`subscription.cancelled` and `subscription.ended` are different days. The first
is the member asking to stop — they have paid through `currentPeriodEnd` and
keep their access until it. The second is the membership actually being over,
and it is the one to revoke on. Cutting somebody off at the first takes away a
month they already bought.

`subscription.payment_failed` is a card that did not go through, not an ending.
Stripe retries for a few days and most of them recover, so treat it as a reason
to email rather than a reason to revoke — `subscription.ended` arrives if it
never clears.

`dispute.opened` fires when a buyer charges back one of your sales, with the
deadline in `dueBy` — usually around twenty days. It is the event to hang
evidence-gathering off, since what wins a case normally lives in your helpdesk
or shipping account rather than in Sailo.

## The envelope

```json
{
  "id": "8f2b…",              // also the webhook-id header
  "type": "order.paid",
  "timestamp": "2026-08-12T09:41:07.221Z",
  "version": 1,
  "test": false,              // true only for the "Send test" button
  "shop": { "id": "…", "handle": "acme" },
  "data": { /* the object the event is about — see below */ }
}
```

New fields may appear inside `data` without the `version` changing. It is bumped
only when something already there changes meaning or disappears, so build your
mapping to ignore fields it does not recognise.

Money is always an object:
`{ "cents": 4999, "amount": "49.99", "currency": "GBP" }`. Use `cents` for
arithmetic and `amount` for anything a person will read — `cents` is correct for
zero-decimal currencies like JPY too, where dividing by 100 is not.

## What is in `data`

Four shapes, one per subject. Which one arrives is decided by the event's
prefix, and every event sharing a prefix carries the identical shape — a
consumer that wired `subscription.created` and later adds
`subscription.cancelled` remaps nothing, because what differs between them is
which one fired and not what a membership is.

| Events | `data` is |
| --- | --- |
| `order.*`, `booking.confirmed` | an order, exactly as `GET /api/v1/orders/{id}` returns it |
| `contact.created` | a contact, exactly as `GET /api/v1/contacts/{id}` returns it |
| `subscription.*` | a membership — [below](#a-membership) |
| `dispute.*` | a chargeback — [below](#a-chargeback) |

The first two are the same objects the REST API returns, so one field map works
against both and the full shape of each is on the [REST reference](/docs/api).

The other two are not, and that is the reason they are written out here. There
is no `GET /api/v1/subscriptions/{id}` and no dispute endpoint, so unlike an
order there is nowhere else to go and read the shape off.

### A membership

Carried identically by all <SubscriptionEventCount /> `subscription.*` events.

No Stripe identifiers are ever included. `stripeSubscriptionId`,
`stripeCustomerId` and `stripeAccountId` all name objects in the *seller's*
Stripe account, and shipping them would let anything holding a payload address
that account directly. The membership's own `id` is the handle Sailo speaks.

<SubscriptionFields />

### A chargeback

Carried by both `dispute.*` events — `dispute.opened` and `dispute.closed`.

Emitted only for a buyer charging back a seller's sale. A seller charging back
their own Sailo subscription is Sailo's money and Sailo's problem, and it has no
business arriving in that seller's Zapier account as though a customer had done
something.

The evidence bundle assembled to answer a case is deliberately absent. It holds
the buyer's address, delivery proof and the seller's own account of events, and
it exists to be sent to Stripe rather than syndicated to whatever an integration
points at. `completenessBp` says how strong the response was without shipping
the response itself.

## Verifying a signature

Sailo signs with [Standard Webhooks](https://www.standardwebhooks.com), so you
can use an off-the-shelf library rather than transcribing a recipe. Three
headers arrive:

```http
webhook-id:        8f2b…             (unique per delivery)
webhook-timestamp: 1786527667        (seconds since epoch)
webhook-signature: v1,K5oZfzN95Z9…   (base64 HMAC-SHA256)
```

```ts
import { Webhook } from "standardwebhooks";

const wh = new Webhook(process.env.SAILO_WEBHOOK_SECRET); // whsec_…
const payload = wh.verify(rawBody, headers);              // throws if invalid
```

By hand: the signed content is `` `${id}.${timestamp}.${rawBody}` ``,
HMAC-SHA256 with the *base64-decoded* bytes of the secret (drop the `whsec_`
prefix first), base64-encoded. Sign the raw body exactly as received —
re-serialising the parsed JSON will not match.

## Delivery and retries

Delivery is at-least-once. A POST that succeeded on your side but timed out on
ours is retried, so **deduplicate on `webhook-id`** — it stays the same across
every retry of one event, while the timestamp and signature are fresh each
attempt.

Answer with any 2xx as soon as you have stored the event; do the work
afterwards. We wait five seconds. Failures are retried after 1m, 5m, 30m, 2h and
12h, then abandoned. Redirects are not followed — a 3xx counts as a failure, so
register the final URL. After 20 consecutive failures the endpoint is switched
off and you are emailed.

### Testing before you go live

The *Send test* button delivers a complete payload with `"test": true` and every
field a real one carries — including the ones that would be null on a shop that
has never had an order. That matters because Zapier builds its whole field map
from the first payload it receives, and a thin sample is a map that breaks on
the first real sale.
