# Changelog

## What counts as breaking

The distinction that decides whether something appears here as a warning or as a
note.

**Not breaking**, and shipped without notice:

- A new endpoint, a new query parameter, a new webhook event, a new MCP tool.
- A new field inside a response body or a webhook `data`.
- A new member of an enumeration — a payment rail, an order status, a dispute
  reason.
- A new error `code`.
- Any change to an error `message`, which is a sentence for a person.

**Breaking**, and announced here before it ships, with the old behaviour kept
working for a stated period:

- A field removed, renamed, or changed in meaning.
- An endpoint removed.
- A webhook event removed, or one that starts firing at a different moment.
- An error `code` renamed.

<Callout type="warning">
The deal is symmetrical. Sailo does not break you with an additive change, and
in exchange **your mapping must ignore fields it does not recognise** and must
not throw on an unfamiliar enumeration member. A consumer that validates a
payload against a closed schema has opted out of that deal.
</Callout>

Two version numbers carry it: `sailo-version` (a date) on every REST response,
and `version` (an integer) inside every webhook envelope. Both move **only** on
a breaking change. See [versioning](/conventions#versioning).

## History

### 2026-08-20 (later) — automations, and a budget you can see

Additive. `sailo-version` does not move.

**Flows.** [`GET /flows`](/api/flows), `GET /flows/{id}` and
`GET /flows/{id}/runs`, plus three matching MCP tools. The runs endpoint is the
one worth wiring: it answers *why did this customer not get the email* without
anybody opening a database. Automations are a Business feature, so a key on a
lower plan gets `forbidden` rather than an empty list — those are different
facts and an integration told `[]` would conclude the seller has no flows.

**Every response now reports the rate budget.** `ratelimit-limit`,
`ratelimit-remaining` and `ratelimit-reset` on every answer, success or
failure, on REST and MCP alike; `retry-after` on a 429.

This reverses something this documentation previously stated as a decision —
that no `Retry-After` was needed because the window is a minute. True, and
needlessly expensive: a caller refused at the fifty-ninth second waited a full
minute for a budget that was whole again one second later. The header now says
which. **Read `ratelimit-remaining` on successes** and slow down before you are
refused rather than after.

**Faster underneath.** Several list endpoints were doing a full sort per page
because no index carried `shop_id` and `created_at` adjacently; `GET /bookings`
was worse than that, scanning across tenants. Nothing about the responses
changed — the same rows in the same order — but paging deep into a large shop
no longer degrades. If you throttled a backfill to be kind, you can stop.

**One cap tightened.** `POST /contacts/{id}/lists` now accepts at most 20 list
ids per array, down from 50. The old ceiling was the number of lists a shop may
*hold*, which is the wrong bound for what one request may *do*. Twenty is well
above what any real integration sends.

### 2026-08-20 — five more resources, and every webhook object now readable

Additive throughout. `sailo-version` does not move, no field changed meaning,
and nothing was removed — an integration written the day before this shipped
needs no change.

**New REST resources.** [Subscriptions](/api/subscriptions),
[disputes](/api/disputes), [bookings](/api/bookings), [staff](/api/staff) and
[lists](/api/lists), each with a list and a fetch-one.

**The gap this closes.** Nine of the <EventCount /> webhook events carried an
object with no endpoint behind it. A consumer that received
`subscription.created`, stored the id and later wanted to know whether that
membership still ran had nowhere to ask — and one that missed a delivery had
lost that state permanently. Every object a webhook carries can now be fetched
back, which is what makes a missed delivery recoverable rather than final.

**A third write.** `POST /contacts/{id}/lists` joins and leaves lists, in the
same add-and-remove shape as tags, and `GET /contacts/{id}/lists` reads the
memberships back. Neither can produce a subscriber on a double opt-in list: the
membership settles as `pending` until the person clicks, and the response says
which state it actually settled in.

**New MCP tools**, one per operation, over the same handlers and the same key. A
read-only key sees only the read tools, as before.

**Server instructions widened.** The MCP `INSTRUCTIONS` string now carries two
further rules a model cannot infer from a tool name: that a cancelled membership
keeps its access until `currentPeriodEnd`, and that a chargeback is not a
refund. Clients that cache instructions from a previous connection should
reconnect to pick them up.

**One refusal fixed.** A `{id}` read with an id that is not uuid-shaped —
`GET /orders/banana` — returned a `server_error` where the honest answer was
`not_found`, because the malformed value reached a `uuid` column. It is a 404
now. Anything branching on the status of that case should expect 404.

### 2026-08-12 — the previous contract

The version every response still carries. It covered <EventCount /> webhook
events signed with Standard Webhooks, and REST and MCP over shops, orders,
products and contacts.

Nothing has been removed or renamed since.

## Watching for changes

**This page** is the signal for anything breaking. Nothing is announced only in
a release note somewhere else.

**The [OpenAPI document](/api/openapi)**, at `/api/v1/openapi.json`, is the
machine-readable version of the REST surface. Diffing it in CI will show you
additive changes too, which is more signal than most consumers want — but it is
there.

**`/llms-full.txt`** is this entire site as one Markdown file, if you would
rather diff prose.

## Deprecations

None currently in force.

When there is one it will appear here with the date it was announced, the date
the old behaviour stops, and what to do instead — in that order, before it
ships.
